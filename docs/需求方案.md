## 0. 一句话定位

**一个零后端、零数据库、零 CMS 的个人内容站**：正文用 Markdown 写、`git push` 即发布，视觉走 Apple 官网那种扁平极简，内容含文章 / 专辑墙 / 工具导航 / 个人简介四块。

维护面被刻意压到最小：**改配置 + 写文章**，没有第三种操作。

### 0.1 永久非商用声明

**本项目为个人非商业用途：无广告、无付费、无商业变现、无赞助。此为长期承诺，不是阶段性状态。**

这条不是一句口号，它是若干设计决策的法律基座：

- 专辑封面（版权作品）的个人非商业使用边界
- 字体与图标资源的许可选择（Inter / Noto Sans SC 均为 SIL OFL，商用亦无碍，但选型时按非商用前提评估）

**若此前提改变（例如日后引入广告或任何形式的变现），上列各项的使用边界必须全部重新评估。**

## 4. 内容模型

### 4.1 文章 `src/content/posts/`

支持两种组织方式，**两者映射到同一个 URL**：

```
src/content/posts/foo.md            → /posts/foo   扁平式，适合无本地图片的文章
src/content/posts/foo/index.md      → /posts/foo   目录式，适合文章自带图片
src/content/posts/2026/foo.md       → /posts/foo   可以按年份/主题分子目录，不参与 URL
```

子文件夹不参与 URL 语义，同名会冲突——这是有意的约束，一篇文章只有一个 URL。

```yaml
---
title: "用 ROS2 写第一个节点"        # 必填，≤60 字（超长会构建失败）
description: "一句话摘要"            # 必填，列表页与 SEO 用
publishedAt: 2026-10-06               # 必填
updatedAt: 2026-10-08                 # 可选，显示"更新于"
category: "机器人"                    # 必填，单值
tags: ["ROS2", "Python", "SLAM"]      # 可选，多值
cover: "./cover.png"                  # 可选，图片放文章同目录。不填则卡片收拢为纯文字
coverAspect: "auto"                   # 可选，封面比例（§6.11）。auto = 按图片尺寸自动识别
draft: false                          # 默认 false，true 则不构建
album: "in-rainbows"                  # 可选，关联专辑 id（双向导流）
toc: true                             # 默认 true
math: false                           # 默认 false；置 true 才加载 KaTeX（LaTeX 语法）
---
```

**公式的写法**：正文里用标准 LaTeX 语法——行内 `$E = mc^2$`，独立成行 `$$\int_0^1 x^2 dx$$`。仅当 `math: true` 时才引入 KaTeX 样式，避免全站为偶尔的公式付性能代价。

**分类与标签的分工（重要）**

- **分类 `category`** = 单值、稳定、几乎不变（如「机器人」「前端」「随笔」）。**现有分类**：`随笔` / `Python` / `数学` / `信息技术`（v1.25 新增，"信息技术"用于系统运维、软件排障等非编程类技术文章）
- **标签 `tags`** = 多值、灵活、随想随加（如「SLAM」「ROS2」「踩坑」）
- **文件夹 ≠ 分类**。文件夹只作物理归档，不参与 URL 语义（已在 `content.config.ts` 的 `generateId` 中强制拉平）。改分类不需要挪文件

### 4.2 专辑 `src/content/albums/<id>/index.md`

封面图与内容文件**同目录同名**：

```
src/content/albums/in-rainbows/
├── index.md
└── cover.png
```

```yaml
---
title: "In Rainbows"
artist: "Radiohead"
year: 2007
type: LP                      # 发行形态，单值，见下
language: "粤语"               # 演唱语种，单值，见下
cover: "./cover.png"          # 必填，本地图片
rating: 9.5                   # 0–10，允许一位小数
genre: ["Alternative Rock"]   # 流派，多值
mood: ["深夜", "写代码"]        # 心情/场景，驱动专辑墙的前端筛选
listenedAt: 2026-09-12        # 首次记录时间，用于排序
pick: true                    # 是否进首页「在听什么」精选
link: ""                      # 可选，可填网易云专辑页地址
draft: false
---

短评正文，支持完整 Markdown。可以是一段话，也可以是一篇完整听后感。
```

**封面图必须放 `src/content/` 下，不要放 `public/`**——放 `public/` 会绕过 Astro 的图片优化管线，既不会转 WebP/AVIF，也不生成响应式尺寸。

#### `type`（发行形态）— 2026-10-10 新增

**五个值，单值**（与文章那边「分类单值、标签多值」同一原则）：

| 值 | 含义 |
|---|---|
| `LP` | 正式录音室全长专辑（**常态**） |
| `EP` | 迷你专（介于单曲与 LP 之间） |
| `Live` | 现场录音 |
| `精选` | 个人精选 |
| `单曲` | **单曲碟**（CDS，一张碟 2–4 首） |

几条约定：

- **这五类是混合维度的**（LP / EP 看曲目规模，Live 看录制方式，精选看曲目来源），所以理论上会有交叉（如「演唱会精选」）。**要补充说明写进正文，不要扩成多值** —— 多值会让标题前的标记变成两个 pill，把标题挤没
- **`单曲` ≠ 三期第二批的「单曲」**。这里指**单曲碟**（一种发行形态）；三期那个是**从专辑里拎出来单独评的一首歌**（独立集合 + `/singles` 页面）。两者各有各的页面，不冲突
- **LP 是常态**：数据里照填（否则筛选栏不会有 LP 按钮），但**卡片上不显示标记** —— 标了它，标记就成了背景噪音，反而看不出「这张不普通」
- **不填 = 无标记**（字段可选、**无默认值**）。不做隐式默认：忘了标就归类错，比「不显示」更糟
- 筛选栏的候选**只从实际数据汇总**，所以不会有空按钮；加一张 EP，它自己就长出来

**展示**：专辑卡片标题前一个中性色小 pill（11px + 淡底 + 次要色）。**不用强调色** —— 全站只有一个强调色，它的语义是「可点 / 当前页」。
**筛选**：专辑墙一行「形态」，与「语种」「心情」是**三套独立条件、同时生效**（AND）—— 先点「Live」再点「深夜」，只剩「现场 且 深夜」。

#### `language`（演唱语种）— 2026-10-10 新增

**单值**，驱动专辑墙的「语种」筛选。**只做筛选，不在卡片上显示** —— 语种回答的是「它属于哪一类」，不是「这张特别在哪」，与 `type` 的标记分工不同。

**为什么不做「港 / 台 / 内地」的地区分类**（2026-10-10 评估结论）：

| | 语种 | 地区 |
|---|---|---|
| 是什么 | 音乐**本身**的属性 | 歌手的**身份归属** |
| 是否直接影响听感 | ✅ 粤语与国语听感完全不同 | ❌ 同地区歌手风格可能天差地别 |
| 会不会有归属争议 | ❌ 无 —— 歌用什么语言唱是**事实** | ⚠️ 有 —— 王菲北京出生、香港出道；李宗盛台湾出道、常驻内地 |
| 扩展方式 | 加一首国语歌就多一类 | 每次都要判断「这人算哪儿的」 |

**决定性事实**：本站 4 位歌手**全是香港**、11 张专辑**全是粤语** —— 按地区分只会有「香港」一项，等于白做。地区视角若日后需要，放 `mood`（灵活、多值的标签）比占一个筛选维度合适。

> **迁移说明**：原先语言值存在 `genre` 里（那字段语义是「流派」），已迁到 `language` 并清空 `genre` —— 同一信息不存两处。`genre` 字段保留，留给日后真正的流派。

### 4.3 单曲 `src/content/singles/<id>/index.md`（三期第二批）

> **状态**：schema 与路由在**三期第二批**落地。第一批先不做——按「**不建空栏目**」原则（与 `/uses` 同一把尺子：空栏目比没有栏目更伤站的信誉），等真有单曲条目再加。

组织方式与专辑完全一致（目录式，目录名即 id 与 URL 段）：

```
src/content/singles/qian-qian-que-ge/
├── index.md
└── cover.png          # 可选：不填则沿用所属专辑的封面
```

```yaml
---
title: "千千阕歌"
artist: "陈慧娴"               # 与专辑 artist 同一套写法（歌手档案靠它匹配，§4.4）
album: "always-your-friends"   # 可选：所属专辑 id。从专辑里拎出来的就填，独立发行的留空
year: 1989
cover: "./cover.png"           # 可选：不填则继承所属专辑的封面，省得为每首歌找图
rating: 9.8                    # 0–10，与专辑同一把尺子
genre: ["粤语流行"]
mood: ["深夜"]
listenedAt: 2026-10-01
link: ""                       # 可选，网易云单曲页地址
draft: false
---

短评正文。
```

**为什么字段与专辑几乎一样**：单曲与专辑本就是同一类「作品」，差别只在 `album` 一个可选字段。代码里**提取共用 schema 片段**，不复制粘贴。

### 4.4 歌手档案 `src/content/artists/<id>/index.md`（三期第一批）

**歌手不是第三份要逐个手写的清单**——绝大多数歌手由专辑的 `artist` 字段**自动汇总**产生；档案只用来给喜欢的歌手补头像、评分与简介。

```
src/content/artists/chen-hui-xian/
├── index.md
└── avatar.png          # 可选
```

```yaml
---
name: "陈慧娴"                     # 必填。显示名，用于匹配专辑的 artist（见下）
avatar: "./avatar.png"             # 可选，不填则歌手墙显示占位图
rating: 9.2                        # 可选，0–10，我的评分（与专辑同一把尺子）
link: "https://music.163.com/..."  # 可选，外部主页
draft: false
---

香港女歌手。1984 年出道，1990 年留学前推出的《永远是你的朋友》是事业巅峰，
整张专辑都绕着「告别」这个主题写。
```

**关键设计：聚合靠显示名匹配，不靠目录名。** 专辑里写的 `artist: "陈慧娴"` 是显示名，而档案目录名是 URL 段（`chen-hui-xian`），两者对不上——若按目录名匹配，就得把现有 11 张专辑的 `artist` 全改一遍。所以**聚合时用 `name` 去比对专辑的 `artist`**：现有专辑一个字都不用改，加一张专辑歌手页自动多一条作品。

**代价**：匹配是字符串相等，写错字（`陈慧娴` / `陈慧嫻`）会**静默**失败。**规避见 §7.9 的构建时校验**（有档案却匹配不到作品的歌手报警）。

**URL 段的来源**：有档案时用**档案目录名**（ASCII）；**没有档案的歌手会退回用显示名**（浏览器会把它百分号编码，能用但不好看）。想让 URL 干净，就补一份档案——构建时会提示哪些歌手还没有档案。

## 5. 专辑墙详细设计

### 5.1 数据来源决议：本地自持（2026-10-06 定稿）

**专辑墙采用本地自持方案：封面由本人上传，元数据与短评手写。不接入任何音乐平台的自动同步。**

#### 为什么排除 Last.fm

Last.fm 的全部价值在于「**自动**同步听歌记录」，而本项目的主要听歌场景是**网易云音乐**——恰好断在最关键的一环：

1. 网易云音乐 App 与桌面端**没有原生 scrobble 支持**，也**没有官方公开 API**
2. 三条绕过路径均不可接受：
   - **麦克风识别**（Shazam / Ambient Music Mod）—— 需长时间开启监听，耗电、识别错误率高，同一首歌会误判成多条
   - **第三方非官方 scrobble 工具** —— 依赖网易云私有接口，随时失效，且有违反服务条款的风险
   - **改用其他播放器** —— 代价是放弃网易云的推荐与歌单，为一面专辑墙不值得
3. 数据源一旦断裂，「自动」就退化为「手动」。既然如此，不如直接手写：少一个外部依赖、少一串失效风险

## 6. 视觉规范：扁平极简 · Apple 风

### 6.1 核心特征

Apple 官网的视觉逻辑可以拆成五条：**近乎单色的配色、陡峭的字号阶梯、极大的分区留白、大而克制的圆角、几乎察觉不到的动效**。没有渐变、没有发光、没有边框线——层次靠留白和背景色差做。

### 6.7 页眉 / 导航栏

**配色刻意避开纯白。** 浅色模式用 `#fbfbfd`（带一丝冷调的近白）配 82% 透明度，深色模式用 `#161617`——两者都是 Apple 官网导航栏的实际取值。配 180% 饱和 + 20px 模糊的毛玻璃，再加一条 0.5px 发丝线，让页眉在每个内页顶部都是一条**看得出来的独立层**，而不是糊进内容里的白块。

| 状态 | 背景 | 文字 | 触发条件 |
|---|---|---|---|
| 常规 | `--header-bg`（近白 / 近黑，82%）+ 发丝线 + 毛玻璃 | `--header-ink` | 所有内页；首页滚动离开首屏之后 |
| 首屏之上 | 全透明、无发丝线、无毛玻璃 | 白色 | 仅首页，`scrollY < 40` |

- 固定顶部，桌面高 48px / 移动 44px
- **透明态只在首页生效**（由 `overHero` 属性控制），用一段紧跟页眉之后的内联脚本切换，早于首次绘制，因此不闪
- 没有 JS 时页眉保持常规状态——安全降级，不会出现白色文字压在白色内容上
- 下拉面板与移动菜单始终使用不透明底色与 `--ink` 文字色，**不受透明态影响**。这里有个坑：不能用笼统的 `.site-header a` 选择器，否则面板里的链接会跟着翻成半透明白，压在浅色面板上直接看不见。规则只作用于显式命名的 `.nav-link` / `.nav-toggle` / `.nav-brand`
- 移动端菜单用原生 `<details>`，零 JS

**三段式布局：站名在左、导航居中、按钮组在右**

导航组的居中**不能**靠 `justify-between`。它只保证「相邻元素间距相等」，不保证中间那组居中——左侧站名 86px、右侧按钮 32px，宽度不等时导航会被推向右方，实测**偏右约 31px**（肉眼很容易感觉「不居中」）。

导航改用绝对定位居中，两侧仍走 `justify-between`：

```html
<nav class="relative mx-auto flex h-full max-w-[980px] items-center justify-between px-6">
  <a class="nav-brand">站点名</a>

  <!-- 绝对居中：脱离文档流，与左右内容宽窄无关 -->
  <ul class="absolute left-1/2 top-1/2 hidden -translate-x-1/2 -translate-y-1/2 md:flex">
    导航项
  </ul>

  <div class="flex items-center gap-3">深浅色按钮 + 移动端菜单</div>
</nav>
```

**为什么不用 CSS Grid `[1fr_auto_1fr]`**：它看似能让中间列自动居中，但**网格自动排布会跳过 `display:none` 的元素**。移动端导航 `<ul>` 是隐藏的，于是右侧按钮组被排进第 2 列（中间），第 3 列空置 —— 移动端页眉整体左移约 135px。要修必须给三个子项都显式写 `col-start`，复杂度反而不如绝对定位。

绝对定位在这里是安全的：导航只在 ≥768px 出现，此时容器内尚有 258px 余量，不会与两侧碰撞。

实测（无头 Chrome 量 DOM + 像素双重核对）：

| 视口 | 导航组水平偏移 | 垂直偏移 | 站名左内边距 | 按钮组右内边距 |
|---|---|---|---|---|
| 768 / 980 / 1100 / 1512 | **0.0px** | **0.0px** | 24px | 24px |
| 390（移动端，导航已隐藏） | — | — | 24px | 24px |

> **测量陷阱**：无头 Chrome 在 Windows 上有**最小窗口宽度**（本机实测约 526px）。请求 `--window-size=390` 或 `500` 时，实际按 526px 排版，截图只是**从左边裁到指定宽度**——于是右侧内容看起来「跑出屏幕」，其实并未越界。判断窄屏布局必须**看 DOM 几何**（`getBoundingClientRect`），不能只看截图。

**固定页眉的连带影响：锚点补偿**

页眉是 `position: fixed`，脱离文档流——浏览器**不知道它占住了视口顶部 48px**。于是任何 `#锚点` 跳转都会把目标压在页眉下面（点目录里的章节名就会遇到）。

解法是 `scroll-margin-top`，让浏览器把这段距离算进滚动位置：

```css
:root {
  /* 与 Nav.astro 的 h-12 对应，改导航高度必须同步改这里 */
  --header-h: 3rem;
}

/* 对所有带 id 的元素生效，而不只是标题——
   这样目录锚点、「跳到正文」的无障碍链接、日后新增的任何锚点都一并解决 */
[id] {
  scroll-margin-top: calc(var(--header-h) + 2rem);
}
```

实测落点：`top = 80px`，页眉高 `48px` → 标题下方留出 32px，未被遮挡。

> **页眉高度抽成 `--header-h` 变量，Nav 与锚点补偿共用同一个值。** 否则改高度时极容易只改一边，产生难以察觉的偏移。

### 6.8 动效

- 入场：`opacity 0→1` + `translateY(20px→0)`，600ms，`cubic-bezier(0.4, 0, 0.2, 1)`
- 用 `IntersectionObserver` 触发，**只播一次**，回滚不重播
- hover：200–520ms，微位移或翻转
- **壁纸轮播**：淡入淡出 1200ms；Ken Burns 持续一个轮播周期，缓慢缩放 1.0 → 1.08
- 全站必须尊重 `prefers-reduced-motion`

### 6.9 反例清单（明确不要做）

- 不要渐变背景、发光阴影、霓虹色
- 不要第二个彩色相的强调色（标签/评分等功能性色除外）
- 不要给每张卡片都描边框——用留白和背景色差分区
- 不要超过两档字重
- 不要弹窗、不要视差滚动
- **不要在正文区放轮播、动效背景等干扰元素**（首屏壁纸轮播是明确例外，见 §6.10）

### 6.10 首页版式与动态背景

**设计张力与调和**

首屏动态壁纸与 Apple 风的纯净底色互相拉扯——背景一旦动起来，正文可读性就崩：对比度不可控、注意力被抢走。

**解法：分区制。** 首屏是"展厅"，首屏以下是"书房"。动效预算全部花在首屏，正文区一分不花。

| 区域 | 处理 |
|---|---|
| 导航 | 固定顶部，毛玻璃 |
| 首屏（`100svh`） | 全屏壁纸轮播 + Ken Burns 缓慢推近，标题叠加其上 |
| 首屏以下 | 回归纯净底色，`#ffffff` / `#f5f5f7` 交替分区，大留白 |
| 页脚 | 极简，与内容区同底 |

这不是妥协——Apple 官网本身即是此结构：首屏满幅大图，正文回到白底。

**动态实现选型**

| 形式 | 观感 | 性能代价 | 决议 |
|---|---|---|---|
| 静态图淡入淡出轮播 | 稳重 | 极低 | 基线 |
| **＋ Ken Burns 缓慢推近** | 有"活"过来的感觉 | 近乎为零（纯 CSS transform） | **采用** |
| 视频背景（无声循环） | 冲击最强 | 3–10 MB，移动端流量负担重 | 不采用 |
| Canvas / WebGL 粒子 | 最炫 | 引入大量 JS，违背零 JS 原则 | 不采用 |
| CSS 动画渐变 | 中等 | 低 | 不采用（渐变违背 §6.9） |

> **关键简化**：「动态背景」与「壁纸轮播」本质是同一件事的两面——轮播是「切换」，动态是「运动」。Ken Burns 轮播一次实现，同时满足两项需求，且**零 JavaScript**。

**深浅色主题下的壁纸处理（成熟方案）**

采用**同一套图 + 主题自适应遮罩**，而不是准备两套图——这是内容站的通行做法，成本最低且效果稳定。

| 主题 | 遮罩 `--hero-scrim` | 理由 |
|---|---|---|
| 浅色 | `rgba(0,0,0,0.30)` | 页面本身是白的，遮罩轻一些，让照片透气 |
| 深色 | `rgba(0,0,0,0.42)` | 页面本身就是黑的，遮罩重一些，让首屏"沉"进页面 |

同时**预留分主题配图**能力，供有需要时启用：

```
src/assets/wallpapers/          共用图（浅色深色都用它）—— 默认
src/assets/wallpapers/light/    浅色模式专用（可选）
src/assets/wallpapers/dark/     深色模式专用（可选）
```

有专用图就用专用图，子目录留空则自动回退到共用图。

**性能红线（硬约束，不得放宽）**

1. 未分主题时：首张图 `eager` + `fetchpriority="high"`，**其余全部 `lazy`**
2. **分主题时例外**：两组都在 DOM 里，靠 `display:none` + `loading="lazy"` 让未启用那组**不下载**，因此首图不能标 `eager`（否则两组会各下载一张）
3. AVIF / WebP + 三档响应式宽度（800 / 1280 / 1920）
4. **单张图 ≤ 300 KB**
5. 移动端（≤640px）降级为单张静态图
6. **必须尊重 `prefers-reduced-motion`**：开启后停轮播、停推近
7. 轮播间隔 **6–8 秒**（当前 7 秒，在 `site.config.ts` 的 `WALLPAPER_INTERVAL_MS`）
8. 叠加文字必须有遮罩层，对比度不低于 **WCAG AA**（用 `--hero-scrim` 纯色遮罩，刻意不用渐变）

**壁纸素材规则**：放入 `src/assets/wallpapers/`，**文件名顺序即轮播顺序**（用 `01-`、`02-` 前缀控制）。建议 3–5 张横构图，1920×1080 以上。若只想给浅色模式单独配图，就在 `wallpapers/light/` 下放图，深色会自动回退共用图。

### 6.11 文章卡片与封面版式

**列表页（`/posts`）：横向卡片**

文字在左、封面在右，整卡铺 `--surface-alt` 底色块（不描边框，遵守 §6.9 的「用背景色差分区」）。

| 项 | 决策 |
|---|---|
| 版式 | 桌面横向（封面固定 220px 宽），移动纵向（封面在上） |
| 卡片外观 | `--surface-alt` 底色 + 18px 圆角 + 24–28px 内边距 |
| hover | 上移 2px，300ms |
| 无封面 | 版式自动收拢为纯文字，不留空位 |
| 点击 | **整卡可点**；「分类」是独立链接，可单独点进分类页 |

首页、标签页、分类页的网格用**纵向卡片**（封面在上、文字在下、不铺底色）——封面本身已是视觉主体，再加底色会显得脏。

**整卡可点，但分类要能单独点**

卡片外壳是 `<article>`，标题是主链接并用**拉伸层**（§6.13 手法 3）铺满整卡；「分类」挂 `.stretch-above` 浮在拉伸层之上。归档页的每一行同理：整行可点，行末分类独立可点；文章详情页标题上方的分类（eyebrow）也是链接。

> **为什么不能把整卡写成 `<a>`**：`<a>` 里再嵌 `<a>` 是**嵌套链接**，HTML 规范不允许——浏览器会拆 DOM，布局会莫名其妙地崩。所以外壳用 `<article>`，「整卡可点」交给拉伸层实现。
>
> 分类全链贯通之前踩过的坑：`/category/[cat]` 路由一直存在，但**全站没有任何内链指向它**（卡片和归档页里的分类都是纯文本），分类页是个只能靠手输 URL 进入的孤岛。

**封面比例：默认自动识别**

`coverAspect` 默认 `auto`——按图片真实尺寸归到最接近的标准比例，**丢图进来就行，不用手填**。需要统一视觉时再显式指定。

| 比例 | 用途 |
|---|---|
| **16:9** | **矩形标准**。文章封面的业界事实标准，且能无损裁进 Open Graph / 社交卡片（1.91:1） |
| 3:2 | 相机直出常见比例 |
| 4:3 | 相机直出常见比例 |
| 1:1 | 正方形 |

> **归类的距离度量用对数距离** `|ln(实际 / 标准)|` 而非差值。比例是尺度无关的量，直接比差值会偏向大比例——1:1 的图到 4:3 差 0.33，到 16:9 差 0.78，用差值会让接近 1:1 的图被误判。

**正文封面：与标题并排，不做整幅大图**

封面放在**标题区右侧**（桌面端固定 300px 宽），不铺满容器。理由：

- 整幅大图（980px 宽 × 16:9 ≈ 524px 高）会把正文压到首屏之外——一进文章先看到一张图，而不是标题
- 与标题并排后，**标题、封面、正文、目录共用同一条左基准线**，页面结构清晰不散
- 移动端封面落到标题**下方**，避免标题被大图挤到屏幕外
- 有封面时不再叠分隔线；无封面时保留一条 hairline 顶替其分隔作用
- 封面同时作为**社交分享图**（`getImage` 生成 1200px 宽的 JPEG），分享出去的卡片才有图

> **排版坑**：本站正文栏宽 680px、右栏（目录）200px，容器内容宽 932px。
> **标题区、正文、相关文章、返回链接必须全部左对齐**（不加 `mx-auto`）。
> 曾经标题区写成 `mx-auto max-w-[680px]`，在 932px 容器里被居中，
> 结果是标题比正文右缩进 126px——视觉上明显错位。

### 6.12 文章内元素：目录、公式、代码块

**目录：导轨 + 每级标记，跟随阅读位置**

| 项 | 决策 |
|---|---|
| 轨道 | 目录左侧一条 1px 线（`--line`） |
| 层级标记 | 二级标题 6px、三级标题 3px（三级文本额外缩进 10px），形成层级差 |
| 当前位置 | 标记加长到 11px 并染 `--accent`，文字转 `--ink`，200ms 过渡 |
| 判定方式 | 滚动时取「**最后一个已越过基准线的标题**」（基准线 = 页眉 48px + 余量） |
| 性能 | 回调走 `requestAnimationFrame` 节流，监听 `passive: true` |

> 为什么不用 `IntersectionObserver`：长章节里 IO 会长时间收不到事件，高亮会卡在上一节。
> 另外必须特判「滚到页面底部」——最后一段可能永远越不过基准线。

目录过长时自身可滚动：`max-height: calc(100vh - 8rem)`。

**公式：KaTeX 样式必须进 `<head>`**

> **真会踩的坑。** KaTeX 会同时输出 **MathML 与 HTML 两套结构**——MathML 供无障碍与复制用，视觉上必须隐藏，而**隐藏规则写在 `katex.min.css` 里**。
>
> 如果样式表放在 `<body>`（例如用 `<link>` 写在文章模板里），首屏会先以**无样式状态**绘制：此刻两套输出同时可见，看起来就是「公式重叠、乱成一团」；样式到达后才恢复。现象时有时无，**很难复现**——按需加载的性能优化反而制造了这个 bug。
>
> 解决：通过 `BaseLayout` 的 **`head` 命名插槽**把样式表送进 `<head>`，同时保持「仅 `math: true` 的文章才加载」的按需策略。另在全局样式加一份 `.katex .katex-mathml` 隐藏规则的**兜底**，即使样式表加载失败也不会叠字。

**公式：KaTeX 的 JS 与 CSS 必须同版本**

> **上一个坑的孪生兄弟，2026-10-09 实测。** 生成公式 HTML 的是 `rehype-katex` 自带的 KaTeX（其依赖声明为 `katex@^0.16.0`），而页面加载的样式表来自**顶层** `katex` 包（当时是 0.19.0）。而 0.19 改掉了三个类名：`sizing` → `katex-sizing`、`strut` → `katex-strut`、`base` → `katex-base`。
>
> 后果极其隐蔽：**分式、大括号、字体、整体结构全部正常**，唯独「下标缩到 0.7em」「strut 撑高」「base 分层」这三类规则因为选择器不匹配而静默失效——**下标以正文字号渲染**，于是 `q_1 q_3` 挤压粘连、`q_1^2` 的上下标叠在一起。**构建不报任何错**，只有肉眼看公式才发现。
>
> 解决：把顶层 `katex` 精确锁到 `rehype-katex` 实际使用的那一个版本（`npm i katex@<ver> --save-exact`），npm 随即去重成**单一副本**，CSS 与 JS 同源。
>
> 判定手法：`node -p "require('./node_modules/katex/package.json').version"` 与 `node -p "require('./node_modules/rehype-katex/node_modules/katex/package.json').version"` 必须一致（后者不存在 = 已去重，更好）；或在浏览器里量「下标字号 ÷ 正文字号」，应为 `0.700`。另：`scripts/prune-fonts.mjs` 只删 `.ttf`/`.woff`，与版本无关，不是元凶。

**公式：矩阵的呼吸感（行距与列距要走两条不同的路）**

> **2026-10-10，令宸反馈「这种大矩阵有点挤」。** 关键约束：矩阵的两种间距都是 KaTeX **在渲染时算好、写进内联样式**的，事后用 CSS 改不动——但两者的干预点不同：
>
> | | 落地形式 | 干预点 |
> |---|---|---|
> | **行距** | 每行纵坐标写成内联 `top:-X.XXem` | 只能用 `\arraystretch`，**必须在渲染时给定** |
> | **列距** | `<span class="arraycolsep" style="width:0.5em">` | `\arraycolsep` **对视觉无效**（只改 MathML 的 `columnspacing`），只能 CSS `!important` 压内联 |
>
> 站点取的两个默认值（都只加宽、不改结构，`cases` / `aligned` / `smallmatrix` 同步受益）：
>
> - `\arraystretch: 1.35` —— 写在 `astro.config.ts` 的 `rehypePlugins: [[rehypeKatex, { macros: { '\\arraystretch': '1.35' } }]]`。LaTeX 默认为 `1`，偏挤。已确认 rehype-katex 会把 `macros` 透传给 KaTeX。
> - 列距 `0.5em → 0.7em` —— 写在 `global.css`，选择器 `.prose-article .katex .arraycolsep`，带 `!important`。**这里是全站唯一必须用 `!important` 的地方**，原因就是上面那条硬约束。
>
> 实测：矩阵列高 `2.98em → 3.673em`；矩阵最密的一篇在 526px 视口下 `scrollWidth == clientWidth`，无横向溢出（`.katex-display` 本就 `overflow-x: auto`）。
>
> 单篇想再松一点，不必改站点配置——正文里直接写 `\def\arraystretch{1.6}` 即可（`\def` 只在那一个数学块内有效）。

**代码块：自动显示语言类型**

Expressive Code **没有**「显示语言」这个配置项——标题栏只认代码围栏上的 `title` 元数据，或代码首行的文件名注释。

解法是在 **remark 阶段**写一个小插件（`src/lib/remark-code-language.ts`）：遍历 mdast，给每个带 `lang` 的代码块补上 `title="<语言>"`。此时 Expressive Code 的 rehype 插件尚未运行，能读到补好的 meta，标题栏就自动显示语言了。

- 代码块自己写了 `title="..."` 时**不覆盖**
  - 副作用：想用「首行文件名注释自动提取」时，显式写 `title` 即可（有 title 就不会去提取注释）

### 6.13 响应式与移动端

断点沿用 Tailwind 默认：**`sm` 640 / `md` 768 / `lg` 1024**。`viewport` meta 为 `width=device-width, initial-scale=1`。

各页面在窄屏下的行为：

| 位置 | ≥768px | <768px |
|---|---|---|
| 页眉导航 | 五项横向居中 | **隐藏**，改为原生 `<details>` 的「菜单」下拉 |
| 首屏壁纸 | 轮播 + Ken Burns | **降级为单张静态图**（`@media (max-width: 640px)` 停轮播、停推近） |
| 文章列表卡片 | 文字左 / 封面右 | 封面移到**上方** |
| 文章详情封面 | 与标题并排（右侧 300px） | 落到标题**下方** |
| 文章目录 | `lg` 以上显示右栏 200px | 隐藏 |
| 专辑墙网格 | 4 列 | 3 列 → 2 列 |
| 关于页 | 照片与文字左右并排 | 纵向堆叠 |

**触控交互层（竖屏专项）**

竖屏没有 hover，用户能感知到的只剩「按下」这一瞬、以及热区够不够大。

| 做法 | 实现 | 理由 |
|---|---|---|
| 去掉 iOS 点击灰闪 | `-webkit-tap-highlight-color: transparent` | 它会和 `:active` 反馈打架 |
| 消除点击延迟 | `touch-action: manipulation` | 去掉「双击缩放」带来的 300ms 判定等待 |
| 按压反馈 | `a:active, button:active, summary:active { opacity: .6 }` | 触屏上唯一的「我点到了」信号。用 opacity 而非缩放/位移，不触发重排 |

**hover 态无需处理**：Tailwind 4 已自动把 `hover:` 包进 `@media (hover: hover)`，触屏根本不触发，所以不存在「点完还留着高亮」。

**热区放大有两种手法，按元素密集程度选**

1. **孤立的小链接 → `.tap-area`**：用 `::after` 覆盖一圈来接管点击，**完全不参与布局**，热区变大而视觉位置一个像素不动。

```css
.tap-area { position: relative; }
.tap-area::after { content: ''; position: absolute; inset: -0.5rem 0; }
```

适用：页脚社交链接（17px → 33px）、页眉站名、文章/专辑页的「← 返回」、首页「全部文章 / 整面墙」、专辑的「在网易云音乐收听」。

2. **密集排列的元素 → 直接给 padding**：`::after` 的外扩量必须**小于相邻间隙**，否则会抢走隔壁的点击。标签 pill 的行间隙只有 8px，所以改用 `py-1.5` + `inline-block` 让行高真的长起来（23px → 29px）。**这是本次唯一可见的改动。**

3. **整块可点、内部还要有独立链接的卡片/列表行 → 拉伸链接**：主链接挂 `.stretch-link`（`::after` 撑满父块接管点击），内部的其他链接（如分类）挂 `.stretch-above` 浮回覆盖层之上。父元素需 `position: relative`。

```css
.stretch-link::after { content: ''; position: absolute; inset: 0; }
.stretch-above { position: relative; z-index: 1; }
```

适用：文章卡片（整卡进文章、分类进分类页）、归档页的每一行。**前提是外壳不能用 `<a>`**（嵌套链接非法，见 §6.11）。

实测（390 / 1180 双宽度 + `elementFromPoint` 命中测试）：卡片内分类链接热区 36×25 / 52×25，点击**命中自身**；卡片角落点击**命中主链接**——两个目标都没丢。

> 测这类热区有个前提：**iframe 不能 `display: none`**。隐藏元素的内部布局全算成 0×0，会得到一堆假 FAIL。要放到 `position: fixed; left: -9999px` 这类「可见但不碍事」的位置。

**元信息 pill 的尺寸基线**（统一后的取值）：文章标签与专辑流派/心情 = `px-3 py-1.5 text-caption`；筛选按钮 = `px-4 py-1.5`；标签云（`/tags`，可点列表项）= `px-4 py-2`；主按钮 = `px-6 py-2.5 text-small`。

**筛选按钮的按下态**：`.filter-btn[aria-pressed='true']`（定义在 `global.css`）= 墨色实心。全站两种状态语义分工——accent 蓝表示「可点 / 当前所在页」，实心墨色表示「正在筛选」。专辑墙的心情筛选与文章列表的分类筛选共用这一套，不在页面里各写一份。

**行内链接不动**：正文句子里的链接（如 about 页的「专辑墙」「Astro」）适用 WCAG 2.5.8 的**行内例外**——为了凑数字把行文断开是错的。

**表格在窄屏横向滚动**

`.prose-article table` 原本是 `width: 100%`，在 390px 下多列表格会被平摊成每列约 50px——数字挤成竖排、读不了，而且它**不会触发页面横向溢出**，光靠溢出审计发现不了。

```css
@media (max-width: 640px) {
  .prose-article table { display: block; overflow-x: auto; }
  .prose-article th, .prose-article td { min-width: 7em; }  /* 不压扁，不够就滚 */
}
```

**实测结论**

| 检查 | 结果 |
|---|---|
| 24 路由 × **320 / 360 / 390 / 414** 四个竖屏宽度 | **96 项，横向溢出 0 项** |
| 注入 6 列表格后 | 表格内部滚动（`clientWidth 342 → scrollWidth 630`），单元格保住 **105px**，**页面未被撑破** |
| 最小有效热区（含 `.tap-area` 补偿） | **29px**（标签）/ **33px**（页脚），门槛 24px ✓ |
| `::after` 是否真的接管点击 | 用 `elementFromPoint` 在上/下各外扩 6px 处验证，全部命中自身 ✓ |
| 移动菜单面板 | 390 / 320 下均不越界，且已加 `max-h-[70svh]` + 滚动 |

**验证方法（可复现，别用窄窗截图）**

无头 Chrome 在 Windows 上有最小窗口宽度（约 526px），`--window-size=390` 得到的截图其实是 526px 渲染结果的**左侧裁剪**，会让人误判「内容跑出屏幕」。正确做法是把页面塞进**真实宽度的 iframe** 里量：

```js
const d = frame.contentDocument;
const over = d.documentElement.scrollWidth > d.documentElement.clientWidth;
// 溢出时再遍历元素，找 right > clientWidth 的元凶
```

三个容易踩空的地方：

- **测 `.tap-area` 这类伪元素热区，必须用 `elementFromPoint`**，`getBoundingClientRect` 量不到 `::after`。伪元素自身尺寸可用 `getComputedStyle(el, '::after')` 读取
- **必须先把目标滚进视口**（iframe 用真实手机高度 844px + `scrollTo`）。若一开始就把 iframe 撑到整页高度，页面里的 `h-svh` 会跟着变成整页高度、把后续元素推出视口，`elementFromPoint` 只会返回 `null`。另外**先关掉 `scroll-behavior: smooth`**，否则滚动动画没跑完，量到的是未滚动的位置
- **测表格/长内容用「注入法」**：往 iframe 的 DOM 里插一张宽表再量，不用真去改内容文件

判断移动端布局**一律看 DOM 几何**，视觉确认则截 iframe（而非窄窗）。

| 知识图谱 | **暂缓**——卡在「边从哪来」，取决于本地知识库有无 `[[双向链接]]` |
| 专辑四件套（口味画像 / 年度十佳 / 评分分布 / 今天听什么） | 暂缓 |
| 其余美化零项 | 归档：`text-wrap: balance / pretty`、`::marker` 定制、引用块装饰引号、暗色模式图片降亮度、按钮填充滑入、标题 hover `#`、章节间隔符、外链 `↗`、空状态友好化、数字滚动动画、导航下划线跟随、图注排版 |

#### 7.2 `/music` 页面结构（从上到下）

> **2026-10-10 改版（令宸验收第一批后推翻原设计）**：原结构为「统计表 → 精选花园 → 货架」。**花园被推翻**（理由见 7.3「为什么放弃错落花园」），改为「**播放器开场 → 统计表 → 封面网格 → 歌手一排 → 收听榜 → 网易云入口**」。骨架不变，换的是「怎么陈列」。

**① 播放器开场** — **全宽一块，占据首屏**（高度约「一屏扣掉页眉」）。

```
┌────────────────────────────────────────────────┐
│                                                │
│   ⬤◯  [黑胶从封面后探出]     千千阕歌          │
│   ┌──────────┐                陈慧娴           │
│   │  大封面  │                这周又在循环      │
│   └──────────┘                                 │
│                                                │
│                    ⌄  （继续下滑引导）          │
└────────────────────────────────────────────────┘
```

左侧一张大封面，**黑胶从封面后滑出、持续慢转**（复用专辑详情页那台纯 CSS 唱片机的做法：`conic-gradient` 沟槽 + 4 道彗尾亮痕做转动参照，见一期第 18 项）。右侧是曲名 · 歌手 + 一句手写话。数据源 `src/data/now-playing.json`（细则见 7.5）。

> **它顺手解开了「黑胶往哪弹」的死结**：详情页的唱片机滑出 40px 是因为左右栏距有 48px，而花园的格距只有 12px——黑胶只要露出超过 12px 就必定压到邻居。**这块是全宽的，黑胶往左探出 60–80px 都不挤**，露出量第一次不再是约束。

**② 统计表** — 一行大数字 + 灰标签，**不超过 4–5 个**（超过就从「开场」变成「后台数据面板」）：

```
11        7         8.6
专辑      歌手      平均分
```

口径与 `/albums` 现有统计条**同源同算法**（同一份数据算出来，否则同一天两个页面数字打架）。两条约束：**只放同类量**（计数 / 平均）——像「最早一张 1990」这类**年份与数量不同类**，混进来会把「开场」变成「数据面板」，**不放**；没有单曲时**不显示单曲数**——空的口径一律不出现。

**③ 封面网格** — 专辑的**整齐网格**（1:1 方图、行列对齐、与 `/albums` 同一视觉语言），标题行右侧挂「**随机抽一张**」按钮。**取全部专辑**（不再区分精选与否）。细则见 7.3。

**④ 歌手一排** — 4 位 + 右侧「查看全部 →」。点卡片**直接进详情页**（跳过列表页，少一次点击）。细则见 7.4。

**⑤ 网易云累计收听榜** — Top 10（7.6）。

**⑥ 网易云主页入口** — 一行小字落款（7.7）。

> **分工（改版后）**：**开场负责仪式感，网格负责好逛**。原设计的「花园负责惊艳 / 货架负责好找」这个分工保留了下来，只是「惊艳」从一堵错落的墙，换成了**首屏那个正在转的黑胶**——后者更点题（这是音乐页，不是照片墙），也不再有裁图问题。

#### 7.3 封面网格与随机抽一张

**为什么放弃错落花园（2026-10-10 实测推翻）**

原设计的「错落」只能靠**尺寸差**（大 2×2 / 宽 2×1 / 竖 1×2）实现，而**本站 11 张封面全是 1:1 方图**（实测最大偏差 1.014）。两者相乘的结果是：

- 非 1:1 的格子（宽格 / 竖格）**必然把方封面裁掉一截** —— 这正是令宸验收时指出的「矩形框图导致截图不完整」
- 只保留 1:1 的两档（大 2×2 / 小 1×1）则失去错落、退化成普通网格；且 `aspect-ratio` 用在**跨行**的大格上会与网格轨道计算打架（实测把大格压成竖窄条）

**横向对照也支持放弃**：搜到的真实项目——`balzss/krater`（明确写着「模拟翻实体唱片收藏的体验」）、`album-shelf`、Albums Adoration、Topster（音乐圈标准格式）、Swiper Vinyl——**没有一个用「大小错落的花园」**。这个领域的「母语」是**整齐的封面网格 + 一个交互**。花园是自创语言，又恰与「封面全是方图」冲突，故放弃。

**改为：整齐网格 + 一个交互**

| 项 | 规格 |
|---|---|
| 布局 | 1:1 方格；列数随断点（移动 2 / 平板 3 / 桌面 4–5），行列严格对齐 |
| 间隙 | 12px（与全站一致，§6.5） |
| 取用 | **全部专辑**，按入坑时间倒序（不再区分精选与否） |
| 卡片 | 复用专辑墙的卡片语言；**点击直接进 `/albums/[id]`** |
| 悬停 | 卡片微抬升 + 封面轻微放大（仅 `@media (hover: hover)` 下） |

**「随机抽一张」** —— 参考 `krater` 的 Random Discovery：一个按钮，点了跳到随机一张专辑详情页。

- **零依赖实现**：URL 列表由**构建时**写进 `data-random-urls`（与 `/posts` 的「随便逛逛」同一手法），点击时前端随机取一条
- 与已有功能不冲突：「随便逛逛」随机的是**文章**，这里随机的是**专辑**

**顺手补一枚信息增量**：网格卡片悬停时可浮出**评分**（原花园卡片只有标题与歌手，评分要进专辑墙翻转才看得到）。

##### 7.3.1 专辑主色（构建时提取）

**做什么**：构建时从每张专辑封面提取一个主色，输出 `src/data/album-colors.json`（`{ "<album-id>": "#rrggbb" }`），供页面读取。

**为什么**：这是从搜到的真实案例里学来的——`Albums Adoration` 的作者明确写过，他试过「自动提取封面颜色」，但最终**每张专辑亲手挑色**效果更好，那个页面的「生命感」主要来自**色彩**而非版式错落。本站做自动提取版（11 张时人工挑色反而更慢；专辑多起来更不可能手工维护）。

**用在哪（克制）**：**只用在专辑详情页** —— 一层极淡的**径向光晕**（封面主色，不透明度约 5–7%），让「看一张专辑」这件事有一点点环境色。**不用在网格卡片上**（一屏彩色光晕会立刻变花哨，违反 §6.2「全站只有一个强调色」）。深浅主题各取一档透明度，保证两种模式下都只是「隐约有色」。

**提取策略**（避免取到「平均色」那种发灰的结果）：

1. 封面**降采样**到小尺寸（如 32×32）
2. 按**饱和度加权**统计，取权重最高的一簇（而非单纯取平均）
3. **亮度钳制**：低于 25% 提亮、高于 85% 压暗 —— 否则深色主题下光晕看不见、浅色主题下刺眼

**四不原则**：✅ **纯构建时计算**，产物是一个静态 JSON，零运行时依赖。

**代价**：构建多一步脚本（挂到 `build`），与 `prune-fonts.mjs` / `subset-noto-font.py` 同类。新增专辑时颜色自动生成，**无需手动维护**。

##### 7.3.2 继续下滑引导

**做什么**：首屏（播放器开场）底沿一枚**轻微起伏的向下箭头**，点击滚到下一段。

**为什么**：播放器开场是一整屏，**不给线索的话，访客可能以为这就是全部**。这是「页面变长」的必要配套（原花园版没有一屏高的开场，所以不需要）。

**规格**：

- 位置：播放器开场块的内底沿，水平居中
- 动画：上下轻移 4–6px，周期约 2s（`ease-in-out`）
- 点击：滚到统计表
- `prefers-reduced-motion: reduce` → **静止**（保留箭头本身，不做位移）
- 滚过首屏后**淡出**（不必一直占着位置）

#### 7.4 歌手体系

**聚合与匹配机制见 §4.4**（靠 `name` 匹配专辑 `artist`，现有专辑零改动）。

**`/artists` 歌手墙**：网格卡片，与专辑墙同一视觉语言。有档案者显示头像 + 评分 + 作品数；**无档案者显示占位图 + 作品数**——没写过的歌手也会自动出现，只是朴素些。**排序**：有评分者按评分降序在前，无评分者按作品数排后。

**`/artists/[id]` 歌手页**：头像 + 名字 + 我的评分 + 简介 + 外链 + **作品区**（复用专辑卡，含 hover 翻转）。没写简介的歌手，这一块只有名字与作品数，**不留尴尬的空白框**。

**专辑详情页**底部新增一块「**这位歌手的其他作品**」——与歌手页双向导流。**这条链通了，栏目才成网**；否则歌手页与专辑页只是两个互不相干的列表。

#### 7.5 播放器开场（原「正在听」的升级形态）

**位置变了**：从「统计表下方一个小块」升级为**页面最顶、占满首屏的全宽开场**。**数据和维护方式完全不变**，变的是体量与职责。

**结构**：左侧大封面 + 从封面后探出的黑胶；右侧曲名 · 歌手 + 一句手写话。

**黑胶的行为 —— 与专辑详情页那台刻意不同**：

| | 专辑详情页（一期第 18 项） | 音乐页播放器开场 |
|---|---|---|
| 触发 | **点击**才转 | **默认就在转** |
| 转速 | 1.8s / 圈 | 更慢，约 3.6s / 圈 |
| 语义 | 「点一下让它转起来」的玩具 | 「**正在播放中**」的状态表达 |

默认转的理由很直接：这块的内容是「我正在听」，**正在听的黑胶当然一直在转**。而且默认转动在**触摸端同样成立**（不存在 hover 依赖，无需降级）。`prefers-reduced-motion: reduce` 时静止。

**复用现成实现**：盘面（`conic-gradient` 沟槽 + 4 道彗尾亮痕）直接搬专辑详情页那套纯 CSS，只调两处——**尺寸变大**、**转速放慢**（见 7.9 风险表）。

**数据源** `src/data/now-playing.json`，**手动维护**——改一次它就更新一次。它不是「此刻正在播放」的技术展示，而是「我最近在听什么」的**手写快照**：

```json
{ "title": "千千阕歌", "artist": "陈慧娴", "album": "pc-always-your-friends", "note": "这周又在循环" }
```

- `album` 填**专辑 id**，用来自动取封面 —— 换一首歌通常只需改这几行
- `note` 是那句手写话，也是这个区块「人味」的来源
- **清空这个文件 = 关掉播放器开场**，页面自动退回普通标题（PageHeader）

**页面介绍文字**：开场右侧、「正在听」之下，由 `src/site.config.ts → MUSIC.intro` 提供（**一行一段**，留空数组则整段不显示）。开场占满首屏、内容本就稀疏，这段是让它「有话可说」的地方（2026-10-10 令宸反馈「页面有点空」后加）。

> **为什么不做自动同步**：主要听歌场景在网易云，而网易云无官方公开 API（§5.1 已定稿排除）。手写快照反而成了本站的独有资产——别人的音乐页告诉你「他听了什么」，本站能告诉你「**他觉得怎么样**」。

> **一处代价**：这块在首屏，封面**不能懒加载**（原花园的图是 `loading="lazy"`）。用 `Picture` 限制宽度档位（800 / 1200 级）即可，属可控增量（见 7.9）。

#### 7.6 网易云累计收听榜

**数据源**：`src/data/listening-stats.json`

```json
{
  "source": "网易云音乐",
  "updatedAt": "2026-10-10",
  "tracks": [
    { "title": "千千阕歌", "artist": "陈慧娴", "album": "永远是你的朋友", "plays": 633 },
    { "title": "夜机",     "artist": "陈慧娴", "album": "秋色",           "plays": 416 }
  ]
}
```

**展示**：Top 10 榜单，每行「名次 · 歌名 · 歌手 · 次数」，挂在 `/music`。

**三条硬约束**：

1. **必须标注来源与口径**。落款两行：`数据来自网易云音乐 · 截至 2026-10-10` / `不含其他平台的收听记录`。第二行别省——它主动交代了「这个数字是什么」；不标就是虚报（网易云只统计它自己 App 里的播放）。
2. **只做累计，不做周榜**。累计是历史沉淀（资产），周榜是瞬时快照（状态）。实测周榜数字太小（Top 1 仅 7 次），上墙显干瘪，还逼人周更。想表达「最近」用 7.5 那句话即可。
3. **独立数据文件，不依赖单曲集合**。榜单是「外部数据的展示」，单曲是「自己的条目」，两者各自生长，以后再关联（建了单曲条目就能从榜单点进详情）。

**更新频率：月更**。令宸提供网易云统计截图 → 录入 → **把读到的数字列出来供核对**（读图可能出错，不默默写入）。没有截图就没有更新，不自行编造、不主动催办。

#### 7.7 网易云主页入口

**纯外链，不做 iframe 嵌入。**

- 地址用带 ID 的干净地址：`https://music.163.com/#/user/home?id=1956997868`。**不用 `163cn.tv` 短链**——它是跳转链，会过期（小红书 `xsec_token` 已有先例）。
- **为什么不嵌入**：iframe 就是「运行时第三方服务」，正是四不原则禁止的东西（与访问统计被否决同一把尺子）；且控制不了它的样式，在极简白底里嵌一块第三方灰色 SPA，观感割裂。
- **放两处**：关于页的个人主页入口（**主入口**，与 GitHub / 小红书 / Instagram 并列，图标**自绘**）；音乐页底部一行小字「在网易云找我 ↗」（场景化入口）。
- **已知事实**（不是劝阻，是让预期准确）：访客点进去，桌面端部分内容需登录、移动端会被强推下载 App。所以**站上的内容比外链重要**——网易云是仓库，音乐页是橱窗，别人记住的是橱窗。

12. **专辑主色** —— 构建时提取 + 专辑详情页淡光晕（独立项，可最后做）

**第二批（等真有单曲内容）**

13. 单曲集合（§4.3）+ `/singles` + `/singles/[id]`
14. `/music` 自动长出单曲段

**顺序理由**：

- **第一批量在「歌手」**，是因为**素材已经在手**——现有 11 张专辑自动汇总出歌手，做完即见内容（歌手墙立刻有东西，只是朴素），本人再挑几位补档案，看着他们「从占位变成有脸」。**单曲则是从零开始**，且第一条得本人真的想写，故放第二批。
- **改版补丁先做 8、9**（网格与开场），因为它们是**页面观感的主干**，且做完立刻可验收；10 依赖 9、11 依赖 8，故排后；12（主色）与版式无关，可独立收尾。

#### 7.9 风险与规避

| 风险 | 规避 |
|---|---|
| 给现有集合加必填字段 → **全部现有专辑构建失败** | **新字段一律可选 + 默认值**，绝不加必填（§9 坑位 14） |
| 歌手名匹配失败（错别字）**静默**失效 | 构建时校验：**有档案却匹配不到任何作品的歌手 → 报警**；有作品无档案是**合法状态**，只提示不报错 |
| 榜单数字被误读为「全平台收听量」 | 落款标注来源 + 口径说明（7.6 约束 1） |
| 页眉加内容后 768px 余量不足 | 导航**不加下拉**（用主页替代），页眉长度不变，无需重新量 |
| 首屏播放器封面**不能懒加载** → 首屏变重 | 用 `Picture` 限宽档位（800 / 1200 级）。单张封面产物已在百 KB 量级（二期字体图片优化后），属可控增量 |
| 黑胶**尺寸放大后沟槽密度失真** | 复用详情页同一套 CSS，只改尺寸变量；沟槽间距与彗尾宽度按比例重调，改完**目视确认「看得出在转」**（一期第 18 项的教训：转动可见性全靠那 4 道彗尾亮痕） |
| 专辑主色在深色主题下过暗 / 浅色主题下过亮 | 构建时**亮度钳制**（<25% 提亮、>85% 压暗）+ 深浅主题各取一档不透明度 |
| 下滑引导的持续动画对前庭敏感用户不友好 | `prefers-reduced-motion: reduce` → 静止显示（保留箭头本身） |

## 8. 部署链路

```
本地写 .md → git push origin main
        ↓
GitHub Actions（唯一通道）
        ↓
npm install（跳过安装脚本）→ 补齐 esbuild 平台二进制 → npm run build
        ↓
上传 artifact → 部署 GitHub Pages
        ↓
https://auraduan.github.io/
```

### 仓库与站点形式

- 仓库名 **`auraduan.github.io`**，属于 GitHub Pages 的「用户站」——站点挂在域名根路径
- 因为挂在根路径，**不需要配置 `base`**（`astro.config.ts` 里也没有）
- 仓库必须 **Public**，否则免费账号的 Pages 不生效
- 建仓时**不要**勾选初始化 README / .gitignore / license——本地已有这些文件，远程初始化会让首次 push 被拒

### Pages 开关（不必手动设置）

`actions/configure-pages` 的 `enablement` 默认为 `true`，首次部署时**会自己把 Pages 打开**。所以「去 Settings → Pages 手动选 GitHub Actions」不是前置条件。

首次推送实测：未做任何手动设置，`https://auraduan.github.io/` 直接上线。手动设置只是更保险。

### 为什么不用官方 `withastro/action`

官方推荐的 `withastro/action` 内部走 `npm ci`，而本项目的 `package-lock.json` **缺少 esbuild 平台可选依赖的条目**——`npm ci` 严格照锁文件安装，会漏掉 esbuild 的二进制，随后以 `generateBinPath` 这种毫不相关的报错把构建炸掉。

成因：npm 对**可选依赖**的安装失败是**静默跳过**的。生成锁文件时本机文件被占用（Windows 上可复现的文件锁问题），这个条目根本没写进去。`npm ci --dry-run --os=linux` 的对照测试证实：sharp 的平台包会被装上，esbuild 的不会。

因此改为手写 workflow，把安装步骤控制在自己手里：

| 步骤 | 做法 | 原因 |
|---|---|---|
| 装依赖 | `npm install --ignore-scripts` | 跳过安装脚本，避免 esbuild 的 postinstall 在二进制缺失时先一步失败，那样连补救机会都没有。本项目所有原生二进制都走 `optionalDependencies`，不依赖 postinstall |
| 补二进制 | `npm install --no-save "@esbuild/linux-x64@$(node -p "require('esbuild/package.json').version")"` | **版本从已装的 esbuild 反查，不写死**，否则日后 esbuild 升级会版本错配 |

### Action 版本（2026-10 实测）

`actions/checkout@v7` · `actions/setup-node@v7` · `actions/configure-pages@v6` · `actions/upload-pages-artifact@v5` · `actions/deploy-pages@v5`

Node 显式指定 **24**（Astro 7 要求 ≥ 22.12），不依赖 action 的默认值以免其变动。

### 其它约定

- 唯一的部署通道，不手写第二个脚本
- RSS 与 Sitemap 都是构建时产出的静态文件，无运行时依赖
- `.env` 与 `.env.*` 已在 `.gitignore` 中排除，保持
- `.workbuddy/` 也已排除——它是会话记忆与临时产物，不是站点内容

## 9. 坑位清单（写代码时避开）

| # | 坑 | 规避方式 |
|---|---|---|
| 1 | 子文件夹进了 URL | 已在 `content.config.ts` 用 `generateId` 强制拉平，不要改回去 |
| 2 | 封面图放 `public/` | 会绕过优化管线，必须放 `src/content/` 下 |
| 3 | Windows 上依赖苹方字体 | 自托管 Inter + Noto Sans SC，不靠系统字体 |
| 4 | 切换深浅色时闪白 | 主题脚本已内联在 `BaseLayout` 的 `<head>`，早于渲染执行 |
| 5 | 已发布的 slug 被改动 | 外链全部失效；需要改时用 frontmatter 显式覆盖 slug |
| 6 | 上线功能与依赖不同步 | 不上的功能，依赖也不装 |
| 7 | 忘记过滤草稿 | 所有列表、RSS、Sitemap、相关文章都走 `lib/content.ts` 的统一过滤 |
| 8 | 首屏壁纸拖慢加载 | 严守 §6.10 七条性能红线 |
| 9 | 壁纸上的文字看不清 | 必须加遮罩层，保证 WCAG AA 对比度 |
| 10 | 深浅色模式下壁纸失配 | 壁纸统一用深色调素材，白色标题在两种模式下都成立 |
| 11 | 入场动效导致内容不可见 | 已有 `<noscript>` 兜底与 `IntersectionObserver` 缺失兜底 |
| 12 | Pagefind 索引 dev 下不存在 | 搜索/命令面板入口在 `npm run dev` 时降级提示；索引由构建脚本在 `astro build` 之后对 `dist` 生成 |
| 13 | pagefind 平台二进制走 npm 可选依赖 | 与 esbuild 同类风险，但**已实测不是问题**：其锁文件条目含全平台 7 个二进制（含 `linux-x64`），CI 无需补齐。装/升级后仍先 `npx pagefind --version` 验证；**另注意任何 `npm install` 都会挤掉 `--no-save` 装的 `@esbuild/win32-x64`** |
| 14 | 给已有集合加**必填**字段 | 会让**全部现有条目**构建失败（三期扩字段时踩）。新字段一律 `optional()` + 默认值，绝不加必填——现有 11 张专辑一个字都不用改 |
| 15 | 章节标题里写行内公式 | 目录文字从标题原样提取，而 KaTeX 输出 MathML / HTML / TeX 三份文本 → 目录显示成「111、222」。标题里写普通字符 |
| 16 | `aspect-ratio` 用在**跨行**网格项上 | 与网格轨道计算打架，实测把 2×2 大格压成竖窄条。方图网格改用「轨道高 = 列宽」或固定行高 |
| 17 | 内联脚本里写 TypeScript 语法 | 带 `data-astro-rerun` 的脚本**不经 esbuild 转译**，TS 语法原样进浏览器 → 语法错误 → 整块脚本作废（页面空白，构建却不报错）。用 `/** @type {any} */ (window)` 断言 |
| 18 | 在无头浏览器里验「滚动才触发」的交互 | headless Chrome 的 `scrollTo` / `scrollIntoView` / `scrollingElement.scrollTop` **全部无效**（`scrollY` 恒 0）→ 这类验收只能真机 |
